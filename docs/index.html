studio.v2.0

Talk to your Laravel project. Approve what ships.

One Ubuntu server, one script, one wildcard DNS record. Studio gives a product team a human interface over Laravel workspaces that live on that server. Every conversation is the person's own Claude Code, running in their workspace with the Larapilot skills of the project: it writes the story, plans it, implements it, opens the pull request. The product manager reads, decides and approves next to the live preview of that branch. Nothing to install on a laptop but a browser.

Release

What's new in 2.0

Studio becomes a place for the whole team. Administrators decide who sees what, project by project; each person works on a project with the role they have there; a project is a hub with its repository, its servers and its passwords next to the chat. The agent gets a browser and sandboxes, and Studio drives the clouds the servers run on. The full list is in CHANGELOG.md.

The team works in projects

A role per project
A person is an administrator, who sees and runs everything, or a member with a role on each project: a developer here may be the PM there and a client elsewhere. The chat, the presets, the MCP servers, the shared passwords, folders and SSH connections and the attached infrastructure all read it. See A role per project.
The project is a hub
Tabs on a row of their own under its header: Workspace, Repository (pull requests, issues, branches, pipelines and releases, with your own account), Infrastructure, Access and, for administrators, Settings, now a page of its own. See The project's tabs.
A key for every project
Studio makes it from the name and six random characters (api-9usaf9). It names the site, the previews, the Linux user and the databases, and never changes; the name is free, so two clients may both have an "API". See A project.
Home
An inbox across every project: conversations that ask something, failed or finished since you last looked; failed workspaces and sites; what waits on each git account. New people get the three steps that make Studio work for them. See Home & the menu.
Infrastructure attached to projects
A Droplet, a server, a zone, a Cipi app or a Boogle project goes into a project's Infrastructure tab, with the roles that see it, the roles that act on it and the actions they may run. Members never see the account behind it. See Attached to projects.
Navigation
The menu keeps its groups: Studio (Home, Projects), Infrastructure, Tools (Git, SSH terminal, Password manager, Drive) and Administration. See The menu.

Accounts and git

Settings → Accounts
Your Claude, Git and SSH keys in one page, three tabs. Add, check and remove your git accounts there, as many as you work with. See Your accounts.
Every git host, always
GitHub, GitLab, Bitbucket Cloud and Azure DevOps are all there for everyone, and a project may live on any of them. A workspace commits with your account on the host of its repository, with that account's name and email. See The git hosts.
Service accounts
The team's own tokens, in Administration → Connectors → Git hosting, create repositories, register webhooks and deploy the sites, and keep doing it when an administrator leaves. See Service accounts.
Tools → Git
One dashboard across all your git accounts: pull requests waiting for your review, issues, notifications, repositories with their branches, pipelines and releases. Review, merge, create. See Git.
Several Claude accounts
Subscriptions, each signed in with Claude Code's own claude auth login in your home on the server, and API keys, side by side; one is your default. The account goes with every message, so a change needs no restart. See Claude accounts.
Groups of projects
Your own groups (Personal, Work, Clients…), each with the Claude account and the git account its projects use; a project may pick others. See Groups of projects.

The agent sees, delegates and works apart

A browser for the agent
A headless Chromium on the server, signed in to the preview as you: Claude opens pages, takes screenshots, reads the console and the failed requests. See The agent's browser.
Screenshots in the chat
Images in tool results show as thumbnails under their call, full size on a click, served only to who may read the conversation.
Subagents as cards
Each subagent is a card with its status, steps, time, screenshots and report; those started together sit side by side. Studio adds code-reviewer and browser-qa. See Subagents.
Conversations in a sandbox
A git worktree of your workspace on its own branch, with a copy of the database and a preview of its own. Several run at once; merge the one you keep, or push its branch. See Sandboxes.
A more readable Changes tab
Each file with an icon for its kind, its name in the colour of what happened to it, and the lines it adds and removes. See Changes, history & branches.

Infrastructure

Connectors
AWS, DigitalOcean, Hetzner Cloud, Cloudflare, Cipi, Boogle, Hackly and Johnny, driven through their APIs, each with any number of accounts: servers, DNS, firewalls, volumes, databases, apps, deploys, exceptions and security findings. For administrators. See Connectors.
Safe by default
Credentials are checked against the provider and stored encrypted; the pages ask for the password again; every action is logged with who did it. Every connector starts off.

Upgrading from 1.1 needs nothing by hand. The update migrates: every membership keeps the role its person had, existing projects keep their keys and their hosts, and the Claude account and git token each person had become their first accounts in Settings → Accounts. It installs Playwright MCP and its Chromium, and gives every bridge its new variables (installer/upgrades/2.0.0.sh). Worth doing once it is live: add a service account and choose it in each project's Settings → General, then attach each project's servers and zones from the connectors' pages.

Quickstart

One server, one script

A fresh Ubuntu 24.04 or 26.04 VPS, a domain, an account on GitHub, GitLab, Bitbucket or Azure DevOps. The installer asks five questions and does the rest.

On the VPS, as root
  1. 1 wget -qO- https://raw.githubusercontent.com/andreapollastri/studio/refs/heads/main/installer/install.sh | sudo bash
  1. The domain. You type it, for example dev.example.com. The script shows the one DNS record to create: *.dev.example.com → A → your server's IP.
  2. The check. It resolves a random name under the wildcard and studio.<domain> through a public resolver and waits until both point at the server. You can skip and fix DNS later; certificates are issued on demand when hosts resolve.
  3. The first administrator. Name and email. The password is generated: the summary shows it, with the dashboard's address and the email, in a yellow box before anything is installed, and again at the end. Save it then; nothing shows it later. Studio has no public sign-up and no social login: accounts are created here and in the dashboard, and people sign in with a password.
  4. Your git host. GitHub, GitLab (gitlab.com or your own), Bitbucket Cloud or Azure DevOps (with its organization): the host of your first token. It does not tie Studio to it: all four, the same forges Larapilot integrates with, are there for everyone, and a project may live on any of them. See The git hosts.
  5. Your token there. With the instructions on screen you create it; the script verifies it with the host and stores it as your first git account. It can create repositories and deploy project sites. Every other person adds their own later; the team's service accounts are added in the dashboard.

Then it installs the newest release of Studio, the latest published vX.Y.Z tag (the head of the main branch only while no release is published; the first release then replaces it), with what it needs: Caddy, PHP 8.3, 8.4 and 8.5 (8.5 alone on Ubuntu 26.04, see below), Composer, Node, Claude Code, the CLI of your git host (gh, glab or the Azure CLI), MariaDB, PostgreSQL and redis. Ten minutes later:

Open the dashboard
  1. → https://studio.<domain>

Sign in, turn on two-factor authentication, add your Claude account in Settings → Accounts. Add the team's service account in Administration → Connectors → Git hosting if you have one, create the first project in Administration → Projects, invite the team in Administration → People and give each person a role on it. From then on Studio updates itself every night to the newest release; see Updates.

Requires: Ubuntu 24.04 or 26.04 LTS (with sudo or Ubuntu 26.04's sudo-rs), amd64 or arm64, 4 GB of memory or more · a domain with a wildcard record · a git account per person on the host of their projects · a Claude subscription or an Anthropic API key per person who chats · Laravel projects with Larapilot (Studio installs it, with Laravel Boost, in the repositories it creates).

DNS and certificates

One wildcard record is enough: *.<domain> → the server. When a browser asks for maria-shop.<domain> for the first time, Caddy calls http://127.0.0.1:8081/api/tls/ask?domain=…; Studio answers 200 for its own host, a project key or a workspace preview it knows, and Caddy issues the certificate. Any other name under the domain shows Studio's welcome page; it gets a certificate too, but only for a few new names a day (STUDIO_WELCOME_CERTIFICATES_PER_DAY, default 3), so that strangers typing random names cannot use up the Let's Encrypt limits the real hosts need. Past that, an unknown name gets no certificate at all.

Trying it on your Mac first?

Studio runs without the server pieces: the local driver points every workspace at one bridge on your machine, driving the claude you already use. composer setup, an admin, composer run dev, then the bridge inside any Laravel project with Larapilot. The demo seeder gives you an agency with five projects (two of them called "API"), four people with a role on each, and a live conversation. See Local development.

Concepts

Five words

Everything in Studio is one of these.

Project

A Laravel repository with Larapilot installed, on any of the four git hosts, its deploy branch, the PHP version and database it needs, the staging site where the deploy branch runs, and the people on it, each with a role there: PM, developer or client. An administrator creates it and Studio gives it a key (shop-k2mx7p) that names its hosts and its place on the server. Its page has tabs for the workspace, the repository, the infrastructure and the access of the person's role, and for administrators its settings. Studio itself never commits to the repository: people and their agents do, with their own accounts.

Workspace

One clone per person × project on the server, under a Linux user of that person: the repository on the deploy branch, dependencies installed, a database of its own copied from the project site, Claude Code running with that person's credential, the bridge. Served at <user>-<key>.<domain>. A PM has one just like a developer: the skills that write the PRD or approve a story need a checkout to commit to.

Conversation

A Claude Code session inside the workspace, kept by Studio with its transcript and its session id, so it resumes days later with its memory. Several conversations can live in one workspace; each is a separate session. A conversation may also run in a sandbox: a copy of the workspace on its own branch, with its own database and preview.

Bridge

A small Node service inside the workspace. Studio sends it the person's message; it drives claude in stream-json mode, posts every event back to Studio, and holds a permission question until the person answers it. Zero dependencies, one process per conversation, released after an idle period.

Project site

The deploy branch, served by the same server at <key>.<domain>. Studio creates it when the project is created, registers a push webhook on its git host, and redeploys it on every push to the deploy branch. Its Larapilot dashboard is what the PM watches; its API feeds the Board; its database seeds new workspaces.

How it works

A request, from words to a pull request

Maria is the PM of Shop Acme. Here is one afternoon, screen by screen.

When the story is reviewed and merged on the deploy branch, the git host calls Studio's webhook and the project site at shop-acme.<domain> pulls, builds and migrates. Its Larapilot dashboard at /larapilot shows the backlog as it is now, to the people of the project once they are logged in to Studio.

What happened underneath

One message
browser→ Studio→ bridge→ claude -p --output-format stream-json

Studio records the message, marks the conversation as working, and hands the text to the bridge of that workspace together with the address and token to call back. The bridge writes one line on the agent's stdin.

Every event
claude→ bridge→ POST /api/bridge/events→ Reverb→ browser

Text, tool calls, results and permission questions come back as small batches. Studio stores them, broadcasts them to the open chat, and polls as a fallback when no websocket is available.

Maria — The client wants to filter orders by date range in the back office. Can we have it by Friday?

Claude — Yes. There is no story for this yet, so I'm adding it as a product request and planning it. US-014 · Date range filter on the orders list. Two tasks, half a day.

Maria — Perfect, go ahead.

Claude — Working on feature/US-014-date-filter. Before rebuilding the assets for the preview I'm asking you: Allow / Deny.

A role per project

A person is either an administrator, who sees and runs everything on every project, or a member, whose role is the project's: a developer on one project may be the PM of another and a client on a third. An administrator sets it in the project's Settings → Members & roles, or in the form of a new project. The role on the person (Administration → People, column Access) says only Administrator or Member · <role> by default: the role a new membership starts with. Changing it leaves the roles on each project as they are.

Everything that belongs to a project reads the role on that project:

  • the chat and the workspace, for PMs and developers, and the project's Repository tab with them;
  • the permission preset a new conversation starts with, and the modes it may switch to;
  • the project's MCP servers, given by role;
  • passwords, drive folders and SSH connections shared with the project by role;
  • the infrastructure attached to the project: who sees it and who acts on it.

The SSH terminal opens to administrators, to developers by default, and to whoever is a developer on at least one project; a project's SSH connections open only to its developers. A change of role counts from the person's next click. Memberships from before roles were per project kept the role their person had.

Presets map to Claude Code's --permission-mode and are set per role in config/studio.php. A conversation starts with the preset of the person's role on the project; Model & mode switches it among the modes that role may use (all four for administrators, PMs and developers). Larapilot's skills and the repository's own are typed as slash commands; see Skills & Claude's questions.

One Claude per person. Every conversation drives the Claude Code signed in with that person's own plan, inside that person's workspace. Studio never holds a shared Anthropic account behind the interface; that is what the terms require and what keeps usage and cost attributable.

Service accounts

A project site is cloned, given its push webhook and deployed with one git account. An administrator's own token works, but it goes when they leave. In Administration → Connectors → Git hosting administrators keep the team's own tokens instead: a bot user, a project or group access token. Service accounts create repositories, register the webhooks and deploy the sites, whoever the administrator is. They are offered first in the new-project form and in the project's Settings → General → Deployed with. Nobody commits with them: people work with their own accounts. A service account that deploys projects cannot be removed until those projects use another one. Its token needs the administrators' scopes below.

GitHub

Organizations. A new repository goes to your account or to an organization you belong to; the form lists the organizations your token can see, and creating a repository there needs the right to do so in that organization. Organizations that restrict fine-grained tokens approve them in Organization settings → Personal access tokens. With SAML single sign-on, a classic token must be authorized for the organization (Configure SSO next to the token).

  1. Where. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Resource owner. The organization that owns the projects, or your account. A fine-grained token reaches one owner: when projects live in several organizations, use a classic token with repo, read:org and admin:repo_hook.
  3. Repository access. The repositories of the projects, or all of them; administrators who create repositories need all of them.
  4. Permissions, everyone. Contents read and write, Pull requests read and write, Metadata read.
  5. Permissions, administrators. Also Administration read and write (new repositories) and Webhooks read and write (the deploy webhook).

GitLab

Groups. A new repository goes to your personal namespace or to a group or subgroup where you are at least Developer and the group lets that role create projects; the form lists those groups by their full path. A self-managed GitLab is the address given with the account (https://git.example.com; the installer's STUDIO_GIT_URL for the first administrator's), and the agent's glab gets it as GITLAB_HOST. Registering the deploy webhook needs the Maintainer role on the repository.

  1. Where. On your GitLab: avatar → Edit profile → Access tokens → Add new token.
  2. Scope. api: clone and push, merge requests through glab and Larapilot, and for administrators the new repositories and the webhook. read_repository and write_repository alone let git work, not merge requests.
  3. Expiration. GitLab asks for a date. Replace the token in Studio before it expires.
  4. Copy it into Settings → Accounts → Git → Add an account → GitLab. It starts with glpat-.

Bitbucket Cloud

Workspaces and projects. A Bitbucket repository belongs to a workspace and to one of its projects. The form lists the workspaces you belong to and their projects: a workspace alone puts the repository in its oldest project, a project puts it there. Creating repositories needs a workspace role that allows it; registering the webhook needs admin rights on the repository.

  1. Where. id.atlassian.com → Account settings → Security → Create and manage API tokens → Create API token with scopes → Bitbucket. API tokens replace app passwords: git signs in with the token as x-bitbucket-api-token-auth, the REST API with the token as a bearer.
  2. Scopes, everyone. read:user, read:workspace, read:repository, write:repository, read:pullrequest, write:pullrequest (each ends in :bitbucket).
  3. Scopes, administrators. Also read:project, admin:repository (new repositories), read:webhook, write:webhook and delete:webhook (the deploy webhook).
  4. Expiration. Up to a year. Replace the token in Studio before it expires.

Azure DevOps

Organization and projects. An Azure DevOps account belongs to one organization, given with the account (https://dev.azure.com/acme; acme.visualstudio.com addresses work too; the installer's STUDIO_GIT_URL for the first administrator's). Another organization is another account. Repositories live in the organization's projects: the form lists them, and a new repository follows the visibility of its project. A project's address must be in the organization of the account that creates or deploys it. Creating repositories needs the Create repository permission on the project; registering the push service hook needs Project Administrator.

  1. Where. https://dev.azure.com/<organization> → User settings → Personal access tokens → New Token.
  2. Organization. This Studio's, or all accessible organizations.
  3. Scopes, everyone. Custom defined → Code → Read & write.
  4. Scopes, administrators. Code → Read, write & manage, and Project and Team → Read.
  5. Expiration. At most a year, or less when the organization's policy says so.

The login on Azure DevOps is the account's e-mail address; the handle is its first part (maria.rossi@acme.com → maria-rossi).

Git accounts

Set up

The project site

<key>.<domain> is the deploy branch, running on the same server. It is the project's staging, its dashboard and the source of every workspace's data.

  1. Creation. When the project is saved, the helper creates a Linux user, clones the deploy branch with the account that deploys it (a service account or an administrator's token), creates the database, writes the .env with APP_ENV=staging and a fresh LARAPILOT_API_TOKEN, runs Composer (dev dependencies included: the site is a staging environment, and Larapilot and Boost are dev dependencies whose dashboard and API it serves), npm, migrations, a PHP-FPM pool, a Caddy host and a queue worker. Studio registers a push webhook on the repository.
  2. Every push to the deploy branch reaches /api/git/webhook/<key> with the project's secret: an HMAC signature from GitHub and Bitbucket, the secret token in a header from GitLab and Azure DevOps. Studio queues a deploy: fetch, reset to the branch, build, migrate, restart the worker. Deploy in Administration → Projects does the same by hand.
  3. The Larapilot dashboard is /larapilot on that host, behind the Studio login like every other address of the project. The PM's bookmark.
  4. New workspaces copy the site's database (a dump and a restore, MariaDB or PostgreSQL), so a person starts from realistic data. Without a site database, migrations run instead.

Deploys are a reset to the branch and a rebuild in place, not atomic releases: a failed migration leaves the site on the previous code, a failed build may leave it mid-way for a moment. It is a staging site, kept simple on purpose. For production use the pipeline your project already has.

Scheduler
A cron line runs php artisan schedule:run every minute as the host's own Linux user. On by default, for the site and for every preview.

Who opens the hosts

Every address of a project is behind the Studio login: the site, its /larapilot dashboard and API, each workspace preview, any path. There is no public mode: a preview runs with APP_DEBUG on, a site with work not yet released, and neither is for the open internet.

Only from
An address list for the site, one for the previews: one IP or CIDR per line. It narrows the login, it never replaces it: from a listed address the visitor still logs in, from any other nobody gets in. Empty means from anywhere, after the login.
Branch overrides

How it works: the Caddyfile puts a forward_auth to Studio's /api/site-auth in front of every host that is not Studio's own, so no project host is ever served without it, whatever its own file says. The bridge hands Studio's servers to Claude Code through a file only the workspace user can read, never on the command line, so a token does not show in the server's process list. It accepts nothing but {"type": "http", "url"} entries from Studio.

Turning it on

Studio's settings live in one file, /opt/studio/shared/.env, shared by every release so an update never touches it. It is owned by the studio user and readable by nobody else; root edits it over SSH. Studio does not read the file on each request but a cache built from it, so a change is live only after a reload, and studio-recover does both in one go:

On the server, as root

Updates

Studio keeps itself up to date. studio-update, run by root, installs every new build of its channel together with what it needs on the server: a new PHP, a newer Node, a package, a git host's CLI, a changed service. The stable channel follows the release tags; beta testers follow the main branch.

Channels

ChannelInstallsFor
Stable (default)The newest release tag, vMAJOR.MINOR.PATCH; pre-releases and everything between two releases are skippedEvery team
Beta (beta tester mode)The head of the main branch, every new commit, before it becomes a releaseA server you test Studio on, not the team's daily work

The channel is a switch in Administration → System; the installer can start on beta (STUDIO_CHANNEL=beta, see What it installs). Neither channel goes backwards: a build is installed only when it contains the installed commit, which the updater checks on a blob-less mirror of the repository. Back on stable after beta, Studio keeps its main build, newer than the last release, until a release contains it; when a release is tagged on that very commit, it moves to the release's name.

When

  • Every night, between 04:00 and 05:00, from a systemd timer, while automatic updates are on (the default).
  • From Administration → System: Check now, then Update to ….
  • Force update, in the same place: builds the newest build of the channel and installs it now, even when it is the one already installed (a broken build, a failed system step, a server changed by hand). The new build goes next to the live one as <build>@<time>, with the same dump and rollback. It never goes back to an older build: that is what studio-update rollback is for.
  • On the server: sudo studio-update apply (--force for the same as the button). Running the installer again does the same as apply.

What an update does

  1. Clone the build into /opt/studio/releases/<build>. A tag's VERSION file must say the same as the tag. With /etc/studio/update-signers in place, the tag (or, on beta, the commit) must carry a valid SSH signature by one of those keys.
  2. System step, as root, from the new build: its installer/requirements.env names the PHP versions, the PHP that runs Studio and the Node major; installer/lib/system.sh installs what is missing, refreshes Composer and Claude Code, installs Playwright MCP at the pinned version with its Chromium, and the CLI of the first administrator's git host. Nothing is removed.
  3. Upgrade scripts, phase before: installer/upgrades/<version>.sh of every version after the installed one up to the new one, in order, as root, for what a release needs beyond packages. On beta, where several builds share a version, a script that changed since it ran runs again.
  4. Build next to the running release, on the shared .env and storage: Composer without dev dependencies, the assets.
  5. Database: a dump to /var/backups/studio/, maintenance mode, migrations with the new code. Caddy's certificate question, the access check of protected hosts and the bridges' callbacks keep answering meanwhile.
  6. Switch: the new build's helper, templates, services, PHP-FPM pool and Caddyfile, then /opt/studio/current points at it; upgrade scripts, phase after; caches, restarts, maintenance off.
  7. Health check: Studio must answer /up. If it does not, or any step from the dump on fails, the previous release, its root files and the database dump come back, and the System page shows the log.

Project sites and workspaces are not touched: they are your projects. Bridges move to the new code when they restart (a workspace stopped and started, a changed token); a release that changes the bridge protocol restarts them in its upgrade script. Three releases and five database dumps stay on disk.

The server itself

Studio's update installs what a release needs and adds what is missing; it does not upgrade what is already there. That is the job of the server update, studio-update system: every night between 03:00 and 03:30 (an hour before Studio's own update, which waits for it), from Administration → System with Update the server now, or by hand. It brings every package and tool on the server to its newest version:

  • apt: update, full-upgrade, autoremove. That is Ubuntu and its security fixes, every installed PHP and its extensions (ppa:ondrej/php), Caddy, MariaDB, PostgreSQL, redis, Node within its major (NodeSource), gh or az. Configuration files changed by hand are kept.
  • Outside apt: Composer (self-update), Claude Code (npm, @latest), glab (its newest release), the azure-devops extension, through the system step of the installed release, which also installs what that release names and is missing.
  • Services: needrestart restarts every service still on an old library (never a workspace bridge, where a conversation may be running: it picks the new Node up at its next start); when anything changed, Studio's services restart; then Studio must answer /up.
  • TLS certificates: Caddy issues each one on demand and renews it by itself when a third of its lifetime is left. The check goes through every certificate Caddy keeps for a host Studio still serves: one past that point gets a TLS handshake on the server, which makes Caddy renew it now; one still not renewed (a DNS record moved, the CA unreachable) is listed on the System page with its days left, until it is. The certificates of deleted projects and workspaces are left to expire. studio-update certificates runs the check alone.
  • Reboot: a new kernel shows reboot required on the System page. With SYSTEM_REBOOT=1 in /etc/studio/studio.env the nightly run reboots the server five minutes after it ends; a run by hand never does.

It stays on what is installed: a new PHP version comes with a release of Studio (requirements.env); a new Ubuntu release, a new Node major or a new major version of MariaDB or PostgreSQL is a decision for a person. The System page lists what the last run changed (php8.4-fpm 8.4.12-1 → 8.4.13-1) with its log; apt's own output is in /var/log/studio-install.log. The switch Nightly server updates (or studio-update system-auto off) turns the timer off.

On the server, as root
  1. ? studio-update check # what the channel would install, and why not
  2. ↑ studio-update apply # --force · --to v2.0.0
  3. β studio-update channel beta # or stable · auto on|off
  4. ↓ studio-update rollback # the previous release and its database
  5. ⚙ studio-update ensure # the system step again · status
  6. ⟳ studio-update system # every package to its newest version, the certificates · system-auto on|off · certificates

Domain & visibility

Every host hangs under the one domain chosen at install: studio.<domain>, <project>.<domain>, <person>-<project>.<domain>, with a wildcard DNS record and certificates Caddy issues on demand and renews by itself. When the domain itself has to change, or a certificate needs a hand, root has studio-domain:

On the server, as root
  1. ? studio-domain status # domain, DNS, visibility, every certificate
  2. ✓ studio-domain check studio.agency.test # does *.domain point here?
  3. → studio-domain change studio.agency.test # move everything there
  4. ⟳ studio-domain renew [host|all] # the late ones · a new one for a host · for all
  5. ✕ studio-domain prune # certificates of hosts no longer served

Changing the domain: create *.<new> A <this server> first; change checks it and refuses to go on until it resolves here (--skip-dns goes on anyway). It backs up every file it touches in /var/backups/studio-domain, puts Studio in maintenance for a minute, moves every site, preview and sandbox (<name>.<old> becomes <name>.<new> in its Caddy host and in the APP_URL, ASSET_URL, REVERB_HOST and session lines of its .env), Studio's own .env and Caddyfile, the hosts kept in the database, and registers every push webhook again at the new address. If a step fails, everything is put back on the old domain. Afterwards everyone signs in again, and passkeys, which belong to the old host, are added again in Settings → Security (passwords and 2FA codes keep working). An app with Reverb on keeps the old host in its built assets until its next build; the command lists them. Once nobody uses the old names, prune removes their certificates.

Certificates: renew alone does what the nightly check does (renews the late ones); renew <host> throws that host's certificate away and gets a new one, renew all every host's. Caddy restarts for it, so open terminals reconnect. Let's Encrypt allows 50 new certificates a week per registered domain and 5 for the same host: renewing everything is for when something is really wrong.

Hiding the dashboard: Administration → System → Domain & visibility switches studio.<domain> from public (its sign-in page to anyone, as any app) to hidden. Hidden, whoever is not signed in gets the page of an address nobody configured, on every path, and the welcome page of unknown names no longer links to Studio. People get in through the door: a secret link shown on that page and next to a new account's password, opened once per browser (it leaves a cookie for a year). A signed-in session is enough, and so is a good password reset link from an email. New link closes every door handed out until then. From the server, studio-recover door prints the link (--rotate makes a new one) and studio-recover public / hidden switch it. Project sites and previews keep their own rules (Who opens the hosts); a hidden dashboard only hides Studio itself.

Locked out

A forgotten password or a lost 2FA device is an administrator's job: the key icon in Administration → People gives the person a new password, shown once, and removes their 2FA (with email set up, people also get the usual Forgot your password? link). Administrators do the same for each other. What is left is the last administrator: nobody above them in Studio, and the server itself fine. The one key that is never in Studio is root on the server. From an SSH session:

On the server, as root
  1. ⚿ studio-recover admin # the main administrator: the oldest admin account
  2. @ studio-recover admin you@agency.test # that account instead; unknown = created

The account gets a new password, printed once in the terminal; its 2FA is removed, every session it had is closed, it is an administrator again with a verified email. Its git and Claude credentials stay, and nothing else on the server is touched. Log in with that password, change it in Settings, set 2FA up again. Each run is written to syslog (auth) and to Studio's log.

studio-recover lives in /usr/local/sbin, mode 0700: only root can read or run it, there is no sudo rule for it and nothing in Studio calls it. It runs php artisan studio:reset-admin as the studio user, which is the same thing if you prefer artisan. Whoever can reset the administrator can already read /opt/studio/shared/.env: the script adds no power root does not have, it only makes the way back short and recorded.

Releasing

For whoever maintains Studio: set VERSION (2.0.0 today), add the release to CHANGELOG.md with what an upgrade from the previous one needs, commit, and push the matching tag (v2.0.0) on a commit that passed the tests. Every stable server installs it at its next run; beta servers already run that commit. The release workflow refuses a tag whose VERSION says otherwise, and so does the updater. To sign releases, tag with git tag -s and an SSH key (gpg.format=ssh), sign the commits of main too if beta servers check signatures, and put the allowed signers, in ssh-keygen's allowed-signers format, in /etc/studio/update-signers on each server. What a release needs on the server goes in installer/requirements.env, or in an upgrade script (installer/upgrades/README.md).

Repository

The project's repository as Tools → Git shows it, without picking it: pull requests (with their conversation and diff), issues, branches, pipelines (Actions on GitHub) and releases. It reads and acts with your own account on the repository's host, the one your workspace commits with, so you may do here what the host lets that account do. Without an account on that host, the tab says so and leads to Settings → Accounts → Git.

Access

The passwords, SSH connections and folders tied to the project, by whoever owns them or by an administrator, in the Password manager, the SSH terminal and the Drive. You see those your role opens. An SSH connection says whether your own key or password for it is set; the SSH group shows only to who may use the SSH terminal. A folder says whether you may view it or view and edit it.

Work

The chat

Three panes: your conversations, the chat, and the right pane with the preview, the changes, the terminal and the files. The chat is Claude Code with a face.

Messages
Yours on the right. Claude's as prose, with Markdown rendered and code inline. System notices, in red when something failed, say what to do.
Streaming
Text arrives as it is typed over Reverb. Without a websocket the chat polls every few seconds while the agent works; nothing is lost either way.
Sessions
A conversation keeps its Claude session id. Close the laptop, come back tomorrow: the next message resumes with the same memory. The title is the first message, trimmed.
Interrupt
Stops the current turn. The process is released; the next message resumes the session.
Status bar
Chips for the state, the Claude account the next message runs on, the model, the effort and the mode; a click opens Model & mode. A subscription shows its plan's usage (the five-hour window and the week); an API key, the estimated cost of the last turn.
Several at once
Open a new conversation for a separate topic. Conversations in your workspace share its branch, so keep one piece of work per conversation, or start it in a sandbox of its own.
Screenshots
Images in a tool's result, such as a browser screenshot or a picture Claude read, show as thumbnails under the call; a click opens one full size.
The list
A dot per conversation: amber while Claude works, blue when it asks you something, red when it failed, green when it finished since you last opened it. The bin deletes one, after a confirmation; only its owner can.

Permissions

Claude Code asks before running a tool its mode does not allow outright. In Studio the question is a card.

The card names the tool, shows the command or the file, and the reason when Claude gives one. Allow runs it with the input shown; Deny tells Claude the person declined, and the turn continues from there. While a question is open the conversation is marked waiting for permission in the sidebar, so a teammate glancing at the list sees who is blocked on whom.

Work

Skills & Claude's questions

The chat is Claude Code: a skill is a slash command typed in the input, and Claude's questions come back as a card to answer.

Skills

Type /larapilot-inception, /larapilot-triage, /larapilot-plan, /larapilot-implement, /larapilot-review or any other skill, with the request after it, as you would in the terminal. Larapilot projects keep their own skills in .larapilot/skills/<name>/SKILL.md, committed with the code, and skills in Claude Code's own .claude/skills/ count too: /acme-predeploy-gate works the same way. Add one from the chat with /larapilot-custom-skill; commit, and every workspace has it at the next start.

Claude's questions

When a skill needs a decision (the effort of a Larapilot setup, how fine the backlog is, the Git mode), Claude asks with its question tool and the chat shows a card: each question with its options and what they mean, one choice or several where the question allows it, and a field for an answer of your own. Answer sends the choices back to the same turn and Claude goes on; Skip lets it go on with its own judgement and say what it chose. The conversation waits for the card like it waits for a permission.

The right pane

Where the conversation's effect shows up: Preview, Changes, Terminal and Files. Clients see the Preview only. In a conversation that runs in a sandbox, all four follow it: its preview, its changes, its files. The arrows after the tabs open the pane full screen, and bring the conversations and the chat back as they were. The preview shows apps that refuse to be framed (X-Frame-Options: DENY): on project and preview hosts Caddy lets Studio, and only Studio, frame them.

Preview
The Laravel app of your workspace on your branch, served by the server at <you>-<key>.<domain>. Open puts it in a tab, which always works; inside the pane the app must not forbid framing (X-Frame-Options). While the workspace is stopped, and for clients, the pane shows the project site.
Changes
A git client for the workspace: the working tree, the history, the branches, the stashes and the tags, read and run through the bridge; see Changes, history & branches. It refreshes after every stored chat event while the tab is open.
Terminal
Allowlisted commands in your workspace, without the agent in between; see Terminal.
Files
The workspace's files in the browser, with the editor of VS Code; see Files.
Over SSH
The workspace is a directory on the server. A developer with SSH access can open it in an editor over SSH; the same Claude session resumes there with claude --resume.
Work

Files

A file manager and an editor for the workspace, in the right pane.

Browse
Folders open on click and load through the bridge; .git is never shown; the button next to the open tabs hides the tree when the editor needs the room. New file, new folder, rename and delete sit in the row menu; a folder is deleted with everything in it, after a confirmation.
Edit
Files open in tabs. Syntax highlighting follows the extension (PHP and Blade, JavaScript, TypeScript, CSS, JSON, Markdown, YAML, shell, SQL…), with VS Code's find, replace, multi-cursor and keyboard shortcuts. The theme follows Studio's light or dark mode.
Save
⌘S / Ctrl+S or the Save button. Every file carries the hash of its bytes from when it was opened; if Claude or a terminal command changed it meanwhile, the save is refused and the tab says so instead of overwriting.
Limits
Binary files and files above BRIDGE_FILE_MAX (512 KB) are described, not opened. The editor is loaded on first use, so the rest of Studio stays light. Everything runs as the workspace's own Linux user, so what a person can edit here is exactly what they could edit over SSH.
Work

Changes, history & branches

The Changes tab is a git client for your workspace, or for the sandbox of the open conversation. Five views: the working tree, the history, the branches, the stashes and the tags. Pull, Push (or Publish for a branch the remote does not have yet) and Fetch sit on top.

Working tree
What is not committed yet: each file with an icon in the colour of its kind (PHP, Blade, JS/TS, CSS, config, docs, images, data, scripts…), its name in the colour of what happened to it (modified, new, deleted and struck through, renamed, in conflict), and the lines it adds and removes with a five-block bar, as on GitHub. Stage and unstage, discard, commit (or Commit & push), amend the last commit. During a merge, pick a side for each conflicting file or edit it and mark it resolved, then commit to conclude or abort.
History
The commits of all branches in date order, drawn as lanes the way editors do: a branch opens a lane, a merge closes it. Refs show as badges (branches, origin/…, tags); search by message, author or id. A commit opens with its message, author, date, files and patch, and its menu reverts it, cherry-picks it, resets to it, starts a branch or a tag from it.
Branches
Local branches with their upstream and ahead/behind, remote branches. Switch checks one out in the workspace; the preview follows, and so does the access rule of that branch. Create, rename, merge into the current one (merge commit, squash or fast-forward), delete here or on the remote.
Stashes and tags
Put changes aside to switch branch, bring them back with Pop or Apply and keep. Tag a commit, with a message for an annotated tag, and push one tag or all of them.

Everything acts on your own workspace, as your Linux user, with your git account on the repository's host. What cannot be undone asks first and says so; a force push says what it replaces.

Terminal

A tab in the right pane runs commands in your workspace, as you, without the agent in between.

It is not a shell. The bridge takes the line, splits it into words, checks the binary and its first argument against a list, refuses anything that looks like shell syntax, and runs the binary directly in the workspace directory. Allowed today:

Output comes in colour: git, Composer, artisan and the test tools are asked for it, and the pane draws the ANSI colours instead of their escape codes. Output is kept to 200 KB and a command is killed after ten minutes. The shortcuts come from config/studio.php; the allowlist lives in the bridge (bridge/src/commands.js), so what the dashboard sends is checked where it runs. Clients have no terminal.

The agent's browser

Claude can look at what it builds. Every chat gets a headless Chromium on the server, signed in to the preview it works on as you.

What it is
Playwright MCP, the MCP server browser of the conversation. Studio installs it with its Chromium on the server; nothing runs in your own browser.
What it sees
The preview of your workspace, or of the conversation's sandbox, with your own pass for that host: the same gatekeeper and access rules as you. A fresh pass comes with every message. It never gets Studio's own cookie.
What it does
Opens pages, takes screenshots, reads the console and the failed requests: that never asks. Clicking, typing and filling forms ask for permission unless the mode allows edits.
Screenshots
Kept on Studio's disk with the conversation, shown as thumbnails under the call that took them (and on the subagent's card), full size on a click. They are served only to who may read the conversation, and removed with it.

On by default; an administrator turns it off for a project in Settings → Agent. Ask for it in plain words ("open the orders page and check the filter on a phone") or let browser-qa do it after a change.

Work

Conversations in a sandbox

Try two ideas at once, or let Claude work on something long while you go on in your workspace. New → Conversation in a sandbox starts a conversation in a copy of your workspace of its own.

  1. The copy. A git worktree of your workspace on its own branch (sandbox/<handle>-<id>), with a copy of the workspace's database, its own build and its own preview at <handle>-<key>--c<id>.<domain>. It takes a moment to prepare; the chat says so.
  2. The work. The conversation runs there, and the Preview, Changes, Terminal and Files tabs follow it: open another conversation and they follow that one. Several sandboxes run at once without touching the workspace or each other. Queues run inline there; the scheduler and Reverb are off.
  3. Keep it. Merge into my workspace, on the bar above the chat, commits what the sandbox holds and merges its branch into the branch of your workspace, all or nothing: a conflict leaves both as they are. Or Push the branch, in the same bar's menu, to open a pull request from it.
  4. Drop it. Remove the sandbox deletes the worktree, its database and its preview, and asks whether to keep its branch or discard it too. Work not committed is lost. The conversation stays, to read.

Up to 3 sandboxes per person by default; an administrator changes the number, or turns sandboxes off for a project, in Settings → Agent. Deleting a workspace deletes its sandboxes.

Work

Workspaces

A workspace is created the first time you open a project, started and stopped from the header, checked against the server every minute.

  • Start / Stop start or stop the bridge and release the preview. Conversations and their sessions stay; a stopped workspace cannot receive a message, and the input says so.
  • What persists: everything, it is a directory and a database on the server: the clone, the dependencies, the Claude login in the person's home.
  • What does not: work that is not pushed, if the workspace is deleted. Keep branches short and pull requests small; the Larapilot loop wants that anyway.
  • Memory: PHP-FPM pools are on demand and a stopped workspace costs nothing; the Claude Code process is released after ten idle minutes and resumed on the next message.
  • Sandboxes live next to the workspace, one per conversation that asked for one (see Sandboxes), and go when it is deleted.
Work

Clients

A client on a project sees it and its staging site as preview, with its Larapilot dashboard behind the same login, and what is shared with the project's clients in its Access and Infrastructure tabs: passwords, folders, servers. No chat, no workspace, no repository, terminal or files, no cost.

It is the role for the person who pays: they follow what is in review and what shipped without opening another tool, and without an email thread. If a client should also talk to the project, give them the PM role on it in Settings → Members & roles; from then on they have a workspace there and need a Claude plan of their own. On their other projects they stay what they were.

Tools

SSH terminal

Tools → SSH terminal, for administrators, developers by default and whoever is a developer on at least one project: real terminals in the browser to any server, opened from Studio's server.

Connections
Host, port, user and a key or a password, saved per person; favourites stay on top. A click opens a terminal; open as many as you like, in tabs or all side by side.
Keys
Generate Ed25519 or RSA 4096, or import yours (OpenSSH, PEM, PuTTY, with its passphrase, which is not kept). The page shows the public key and the command that adds it to authorized_keys. The same keys are in Settings → Accounts → SSH keys.
Host keys
The first connection shows the server's fingerprint and asks; from then on a different key is refused.
Shared with a project
Tie a connection to a project and the administrators and the project's developers find host, port and user ready, tagged with your name, here and in the project's Access tab. Each connects with a key or password of their own: credentials are never shared.

Private keys and passwords are encrypted with APP_KEY and never reach the browser. The page asks Studio for a one-time ticket (60 seconds) and opens a WebSocket to the gateway, studio-ssh (ssh-gateway/, behind Caddy at /ssh/ws), which redeems the ticket on the loopback and only then sees host and secret. The page asks for your password again, as Settings → Security does.

Tools

Password manager

Tools → Password manager: the team's credentials, encrypted on the server, shared on purpose.

  • Items: title, URL, username, password, notes and a two-factor secret (base32 or otpauth://), for which Studio shows the current code. A generator makes passwords of any length.
  • Folders: yours, nested, to put your own items in order, and to share many at once (below).
  • Projects: tie an item to a project and tick which roles on that project see it: clients, PMs, developers. It shows in the project's Access tab too. Administrators see every project item.
  • People: share an item with a single person, to view or to edit. The sharing dialog shows who sees it and why.
  • Shared folders: Sharing in a folder's menu shares it as an item is shared, with a project for the roles ticked and with single people, to view or to edit. Everything inside it goes with it: its items, the folders inside it and what is added later. Who receives it finds it under Shared folders, with the folders inside it; who may edit changes the items and adds new ones, which stay the owner's. The folder itself, its sharing and removing items stay the owner's. A folder tied to a project shows under the project and in its Access tab; an item's sharing table says which folder brings it to whom.

Everything but title and URL is encrypted with APP_KEY. Secrets do not sit in the page: they come from the server when you press show or copy. Personal items stay personal, also for administrators; clients see what is shared with them and create nothing.

Drive

Infrastructure

Connectors

The clouds and services your servers run on, driven from Studio through their APIs: AWS, DigitalOcean, Hetzner, Cloudflare, Cipi, Boogle, Hackly and Johnny. Servers, DNS, firewalls, volumes, databases, apps, deploys, exceptions and security findings, without opening seven consoles.

For administrators
Connector pages exist only for administrators. PMs, developers and clients never see the menu, the pages or the accounts; they see only what an administrator attached to their project, in its Infrastructure tab.
On or off
A connector is off until an administrator turns it on. Only the ones that are on appear in the menu, in the folding Infrastructure group after Tools.
Many accounts
Each connector holds any number of accounts: several AWS accounts, a DigitalOcean team per client, a Hetzner project each, one Cipi server each, several Boogle, Hackly or Johnny instances.
Credentials
Checked against the provider before they are saved, stored encrypted with APP_KEY, never shown again and never sent to the browser.

Turn a connector on

  1. Administration → Connectors. Each card says what the connector drives, how many accounts it has and how many of its things are attached to projects. Below the cards, Git hosting holds the team's git service accounts.
  2. Flip the switch. The connector shows in the menu right away; Open (or Add an account when it has none) takes you to its page.
  3. Turning it off removes it from the menu and closes its pages at the next click. Its accounts, and what is attached to projects, stay, ready for when it is turned on again; delete them from the connector page if they should go.

Accounts

On a connector's page, Accounts (top right) lists the accounts with their state (working or failing, what the provider answered, when it was last checked) and opens the form.

  • Add: Add an account, a name the team recognises (Production, Client X, eu-server-2), the credentials the provider's page below describes, then Check and save. Studio calls the provider with them first: a wrong or too weak token is refused with the provider's own words and nothing is saved.
  • Check: the signal button asks the provider again, for instance after changing the token's permissions there.
  • Rotate a token: create the new one at the provider, Edit the account, paste it, save; then revoke the old one at the provider. Secret fields are empty in the form: left empty, the stored value stays.
  • Remove: deletes the account from Studio. The token still works at the provider until you revoke it there.

The links in the form lead to the page of this guide for that provider and to the provider's own documentation.

Working on a connector page

  1. Account: the menu at the top picks the account; the arrow next to it reads everything again from the provider.
  2. Tabs: one per kind of thing (Droplets, Zones, Apps…). AWS has many, so they come in groups (Account, EC2, Lightsail, Databases, Storage & CDN, Route 53): the first row picks the group, the second the tab.
  3. Search and filters: the search box filters what is on screen; filters ask the provider again: the region for AWS, the Cloudflare account, the status of Boogle exceptions and Hackly findings.
  4. Create: the dark button on the right (New Droplet, Add a zone, New app…) opens a form. Choices such as regions, sizes, images, SSH keys or servers come from the provider for the account and region picked.
  5. Row actions: the … menu at the end of a row holds what can be done on it; only the actions that make sense in its state show (no Start on a running server). Buttons on the row itself open what lives inside it, such as the DNS records of a zone or the aliases of a Cipi app; the arrow at the top left goes back.
  6. Attach to a project: the … menu of a row also has Attach to a project…, and a badge on the row names each project it is attached to. See Attached to projects.
  7. Confirmations: anything that stops, deletes or overwrites asks first, in words that say what will happen. Actions with a form ask when the form is sent.
  8. Results: what an action hands back (a new root password, a generated private key, a database password, the nameservers to set, a TXT record to publish, logs, a zone file) opens in a window with Copy. Secrets are shown once: store them, for instance in the Password manager. When the provider is still working in the background (a Cipi deploy, for instance), the window says so and Check again asks once more.

Lists are cached for two minutes per account, so moving between tabs is quick and providers' rate limits are spared; every action from the page, and the refresh arrow, clear the cache of that account. A change made in the provider's own console shows here within two minutes, or at once with the arrow.

Safety. Every administrator can do, on every connector account, everything its credentials allow. The pages ask for your password again, as the SSH terminal does. Give each account the narrowest token that does its job (read only where nobody needs to act), and keep tokens with an expiry where the provider offers one. Every action is written to Studio's log, /opt/studio/shared/storage/logs/laravel.log on the server, as an infrastructure line with the person, the connector, the account, the tab, the action and the row, and the project resource when it ran from a project's tab: grep '"infrastructure"' laravel.log.

Security

  • Accounts: invite-only; email and password with two-factor and passkeys; roles, read on each project, enforced by policies on every page and action.
  • Previews and sites: served over HTTPS by Caddy. A preview runs with APP_DEBUG=true: every project host is behind the Studio login and the project assignment, narrowed by the access rules (address lists, branch overrides), which Caddy checks before the app sees the request. Studio's own session cookie never reaches a project host.
  • Bridge: listens on the loopback only, one port per workspace, with a token per workspace. Its callbacks carry a second token per workspace that Studio stores hashed and matches on every request.
  • Root: only studio-admin, through sudo, for named commands with validated arguments. Studio never runs shell commands of its own.
  • Secrets: git and Claude tokens, bridge and callback tokens, webhook secrets, MCP server headers and the Larapilot API token are encrypted at rest with the app key. On the server, each person's tokens sit in a root-owned file readable by their Linux user only, and git gets the token from the environment through an askpass helper, never from a file.
  • The agent: runs as ws-<user>; Unix permissions keep it out of other people's homes and out of the project sites; managed settings deny reading the login files (~/.claude-* too) and disable bypass mode. It is not a kernel boundary between two workspaces of the same person. Its browser carries only the pass of the preview host it works on, and Chromium keeps its own sandbox.
  • Infrastructure: connector accounts are the administrators', checked and stored encrypted; their pages ask for the password again. Members reach only the rows attached to their projects and the actions handed to their role, checked on the server for every call, and every action is logged with who did it.
  • Updates: studio-update runs as root and installs the release tags of the repository in studio.env (and, on a beta server, the head of main). Whoever can push such a tag, or push to main for beta servers, can run code as root on every server that updates from it: protect the tags and the branch, sign them, and list the allowed keys in /etc/studio/update-signers so an unsigned or foreign build is refused. Turn the nightly updates off to read each release before installing it.
  • Transport: HTTPS everywhere; Studio's loopback listener on 8081 serves only the TLS question, the access check of protected hosts and the bridges' callbacks.

For zero public exposure put the server on a tailnet; then every person needs the client. Most agencies will keep Studio public with two-factor on.

config/studio.php holds the permission preset and the allowed modes per role, the model and effort lists, and the terminal shortcuts. What changes per project (services, access rules, MCP servers) lives in the project settings, not in files. /etc/studio/studio.env holds what the helper and the updater need: the domain, the paths, the PHP that runs Studio, the repository releases come from (STUDIO_REPO), AUTO_UPDATE, UPDATE_CHANNEL (stable or beta), SYSTEM_UPDATE (the nightly server update, on by default) and SYSTEM_REBOOT (off by default).

Local development

Terminal
  1. 1 composer setup && php artisan studio:make-admin
  2. 2 composer run dev # server, queue, logs, vite · add: php artisan reverb:start
  3. 3 cd ~/code/some-laravel-app && BRIDGE_TOKEN=local-bridge-token WORKSPACE_DIR=$PWD node ~/code/studio/bridge/bin/bridge.js

The bridge drives the claude on your machine with your login. Create a project in Administration, add yourself, open it: with the local driver the workspace is running at once and the chat talks to that bridge, no git or Claude account needed. php artisan db:seed --class=DemoSeeder gives the agency of the screenshots, password password for everyone.
